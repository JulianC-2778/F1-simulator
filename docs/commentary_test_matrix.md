## 2. Event vocabulary check

Task book asks for `contact / position_change / off_track / lap_complete / battle /
pace_surge / pace_update`. All seven exist verbatim in `EVENT_PRIORITIES` /
`EVENT_COOLDOWNS` (`commentary_engine.py:15-33`) — no renaming needed.

| Event | Priority | Cooldown (s) | Trigger condition (from code) |
|---|---:|---:|---|
| `contact` | 5 | 1.0 | `damage_delta >= 5.0` |
| `position_change` | 5 | 1.0 | `latest.race_pos != last_race_pos` |
| `off_track` | 5 | 1.2 | `abs(track_pos) > 1.0` and wasn't already off |
| `lap_complete` | 4 | 1.0 | `latest.lap > last_lap` |
| `battle` | 4 | 2.5 | `front_gap < 10.0` and `speed_x > 60.0` |
| `pace_surge` | 3 | 2.5 | `speed_x - prev.speed_x > 22.0` and `throttle > 0.8` |
| `pace_update` | 1 | 6.0 | `sim_time - last_commentary_sim_time >= baseline_interval` (default 10s) |

Plus two cooldown layers not tied to a single event: a global 1s wall-clock cooldown
between *any* two emitted events (`_can_emit_event`, `commentary_engine.py:145-152`),
and a 10s (configurable, `dedupe_seconds`) text-level dedup applied to the *generated
reply text*, independent of the event cooldown (`should_emit_text`, L122-130).

## 4. Fixed defect: text dedup ran after the broadcast, not before it

`_run_commentary()` (`runtime.py`) used to call `commentary_engine.should_emit_text()`
**after** `generate_commentary()` had already unconditionally broadcast `ai_done` +
`tts_audio`; the dedup result was only used to write a log line
(`"重复解说已被去重记录标记"`), never to suppress the broadcast. Net effect: if two
different events (different `event_type`/`reason`, so neither is blocked by the
per-signature event cooldown) produced identical or near-identical model text within
`dedupe_seconds` (default 10s) of each other, the duplicate text really was sent to
every WebSocket client twice — the exact failure mode task-book §5.5's first forced
regression test describes. Two of the four browser/Overlay consumers
(`midware/static/index.html`, `midware/static/index2.html`) additionally never looked
at `ai_done.content` at all — they render purely from the accumulated `token` stream —
so even a backend-only fix would not have stopped real users from seeing it.

**Fix applied** (commit-local, not yet committed by this session — see final summary):
- `midware/runtime.py::generate_commentary` now calls `should_emit_text()` itself,
  before the TTS call and before the `ai_done` broadcast. A duplicate is broadcast with
  `content: ""` and a new additive `duplicate: true` field; TTS synthesis is skipped.
- `midware/runtime.py::_run_commentary` no longer makes its own second, now-redundant
  call to `should_emit_text()` (that second call had a latent bug of its own: the
  function has a side effect of stamping `text_history`, so calling it twice on the
  same reply text always made the *second* call report "duplicate", regardless of
  whether it actually was).
- All four consumers (`overlay-app/src/renderer.js`, `midware/static/index.html`,
  `midware/static/index2.html`, `midware/static/dashboard.html`) now check
  `message.duplicate` and discard their streamed buffer instead of falling back to it.
- Regression test: `tests/integration/test_commentary_runtime.py::TestDedupeBeforeBroadcast`
  (written first, confirmed failing against the pre-fix code, then confirmed passing
  after the fix; full `tools/run_tests.sh` + `--only L3` re-run clean, see §6 for counts).

**Real-world severity**: low-probability (persona already instructs the model "do not
repeat the previous line", so two independently-triggered events producing literally
matching text is uncommon), but it directly undermines the "duplicate user-visible
displays = 0%" target that work package D's endurance test measures — so it was worth
fixing even though it isn't a crash-class bug.

## 5. Confirmed defect: 45-word cap is not enforced

`CommentaryConfig.max_words` (default 45) flows into
`build_commentary_payload()` as `payload["style"]["max_words"]`
(`commentary_engine.py:420-423`). But the function that turns that payload into the
actual prompt text sent to the model, `format_event_fields()`
(`context_manager.py:94-115`), explicitly skips the `style` key via
`_EVENT_FIELD_SKIP = {"task", "style"}` (`context_manager.py:91`). `generate_commentary()`
(`runtime.py:365-460`) also performs no post-generation truncation of the model's reply.

Net effect: for event-triggered commentary, `max_words` is stored in config and
returned by `/api/commentary/config`, but **never reaches the model as an instruction
and is never enforced on the output**. It is UI-visible dead configuration.
Reproduced by `tests/integration/test_commentary_runtime.py::test_max_words_is_not_enforced_by_code`
(fails before any fix — see that test's docstring for the exact assertion).
Per the task book's rule ("increase scope of failure-reproducing test before fixing,
then run full regression"), this repository run does **not** apply a fix — only
reports and regression-guards the gap — because deciding *whether* to enforce it (hard
truncate vs. prompt-level instruction vs. leave as documentation-only) is a product
decision, not a testing one.
